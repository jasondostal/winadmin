# Live-Fire Test — 2026-06-18

Dogfooding `fleet` over the **real SSH transport** against a fleet of 10 independent
`sshd` endpoints. The goal: turn the SSH path from "compiles and vets" into
"observed working end-to-end," and find whatever breaks when you actually run it.

**Result: SSH transport proven.** 10/10 hosts, secure host-key verification, key-based
auth, a non-standard port, bounded concurrency, a verified remote change, and correct
mixed-failure handling. Two real gaps were found and fixed along the way.

---

## What we wanted vs. what we got

The plan was 10 cheap Azure VMs. Azure had other ideas — see the war stories below — so
the fleet ended up as **10 Docker `sshd` containers on a a single Linux control host**,
each on its own bridge IP with `lscr.io/linuxserver/openssh-server` listening on 2222.

**Honest caveat:** these are containers on one host, not 10 separate machines. What that
does and doesn't prove:

- ✅ Proven for real: the SSH client transport, public-key auth, `known_hosts`
  verification, custom port, the bounded worker pool, per-target results, the audit
  trail, and that a command actually executes on each remote endpoint (verified
  out-of-band).
- ⚠️ Not exercised: WAN latency/jitter, real per-VM network isolation, cloud auth. Those
  wait for a cloud run (one `gcloud auth login` away).

The transport itself cannot tell the difference between a container's `sshd` and a VM's
`sshd` — it's the same protocol over the same TCP path — so this is a legitimate proof of
the client code.

## The fleet

```
docker network create lflab
for i in 01..10:
  docker run -d --name lf$i --network lflab --hostname BR$i-DC01 \
    -e PUBLIC_KEY="$(cat id_test.pub)" -e USER_NAME=svc -e PASSWORD_ACCESS=false \
```

Inventory = the 10 container bridge IPs (172.18.0.2 … 172.18.0.11). Host keys were
collected the secure way — `ssh-keyscan -p 2222` into a `known_hosts` file — so the run
used **real host-key verification**, not the insecure skip.

## Run B — apply a real change, verify out-of-band

The run wrote a host-stamped file on every target; verification was done *independently*
with `docker exec`, not by trusting `fleet`'s own output:

```
$ fleet run ... -P 5 -c 'echo "winadmin was here on $(hostname) at $(date -u +%H:%M:%SZ)" > /tmp/winadmin.txt'
total=10  succeeded=10  failed=0  skipped=0   elapsed=127ms

$ docker exec lf03 cat /tmp/winadmin.txt
winadmin was here on BR03-DC01 at 03:28:00Z
$ docker exec lf07 cat /tmp/winadmin.txt
winadmin was here on BR07-DC01 at 03:28:00Z
```

Each box ran the command locally and produced output containing *its own* hostname — proof
the work executed remotely, not on the control host.

## Gaps dogfooding found (and fixed)

Running it for real beat reading it. Two things were broken/missing and would not have
surfaced from tests alone:

1. **SSH transport had no auth wired into the CLI.** The library `SSHTransport` accepted
   `Auth []ssh.AuthMethod`, but `cmd/fleet` never populated it — an SSH run would have
   failed to authenticate against anything. Fixed by adding key-file (`SSHKeyAuth`) and
   ssh-agent (`SSHAgentAuth`) resolution, lazy per-connection, plus `--ssh-key`.
2. **No way to target a non-22 port.** The containers' `sshd` listened on 2222 and there
   was no flag for it. Added `Port` plumbing and `--ssh-port`. (Real-world relevant:
   Windows OpenSSH and jump setups routinely use off-22 ports.)

Both are the kind of gap that "it compiles" hides and a live run exposes in seconds.

## War stories (the real-sysadmin part)

- **Azure capacity lock.** Every VM size tried — `B1s`, `A1_v2`, `DS1_v2` — failed
  `SkuNotAvailable` ("Capacity Restrictions") across `eastus`, `eastus2`, `westus2/3`,
  `centralus`, `canadacentral`, `southcentralus`, all three zones, and even Spot. This
  pay-as-you-go subscription is capacity-restricted by Azure (common for newer subs until
  they age in). Quota wasn't the blocker — capacity was. A genuine wall you hit in the
  field, not a config error.
- **azure-cli 2.87 error-masking bug.** Every failed `az vm create` surfaced only
  `RuntimeError: The content for this response was already consumed` — the CLI's own error
  formatter crashed trying to display the ARM error, hiding the real `SkuNotAvailable`. The
  actual cause was only recoverable via `--debug` and reading the raw HTTP response. (Worth
  a note for anyone debugging az: when you see "content already consumed," re-run with
  `--debug` and grep for `Exception Details`.)
- **AWS / GCP both needed interactive reauth** (`aws login` SSO expired; `gcloud auth
  login` token refresh failed under non-interactive execution), which is why this run
  landed on the Docker lab. The cloud run remains a 20-second reauth away.

## Cloud run (AWS EC2) — the WAN proof

After the container lab, AWS was reauthenticated and the same test was run against **10
real `t2.micro` instances in `us-east-1`**, driven from a Linux control host over the open
internet. This is the part the container lab *couldn't* prove: real per-VM isolation and
real WAN latency.

Setup was scoped securely — SSH ingress allowed only from the control host's public IP (`/32`, not
`0.0.0.0/0`), a throwaway imported key pair, host keys collected via `ssh-keyscan` (10/10),
AL2023 AMI resolved from SSM.

**Run A — identity, 10 boxes, pool of 4:**

```
targets=10  parallel=4  transport=ssh (user=ec2-user, port=22)  mode=EXECUTE
[1/10] 54.152.169.0   ok
... (all 10) ...
total=10  succeeded=10  failed=0  skipped=0
elapsed=3.48s
```

10/10 over real internet SSH. Note **3.48s** vs the container lab's 154ms — that delta is
genuine WAN round-trips and per-host SSH handshakes.

**Run B — real output via `-v` (a third gap found & fixed):** the tool captured stdout but
had no way to display it. Added `-v`. Output shows the instances really are distinct and
spread across the AZ:

```
[1/10] 34.227.197.238   ok
        | ip-172-31-28-240.ec2.internal AZ=us-east-1b
[2/10] 3.90.68.151      ok
        | ip-172-31-23-250.ec2.internal AZ=us-east-1b
...
```

**The concurrency payoff, measured over WAN** — same 10 hosts, `sleep 1` each:

| Mode | Flag | Elapsed |
|------|------|---------|
| Sequential | `-P 1` | **19.64 s** |
| Parallel   | `-P 10` | **2.01 s** |

A ~10× wall-clock win — exactly why a bounded worker pool matters, now quantified
against real latency. Over 350 servers and a multi-minute task, that's the difference
between an overnight job that finishes and one that doesn't.

**Gaps found across the whole live-fire (all fixed):** (1) SSH auth not wired into the CLI;
(2) no `--ssh-port`; (3) no way to show command output (`-v`). Three real gaps, none of
which a passing unit test would have caught — only running it did.

## AD/LDAP run — "set a property on every user in an OU"

The directory counterpart to the machine fanout: instead of a host list, the inventory is a
**live LDAP query**, and the action is a **bulk attribute modify**. Lab was an OpenLDAP
container (`osixia/openldap`) with an `ou=people` of six users — the same LDAP protocol AD
speaks; the AD-specific search filter is the documented default and was overridden to
`(objectClass=inetOrgPerson)` for the lab schema.

Two capabilities were added to make this first-class, **with no new dependency** — the tool
shells out to `ldap-utils` (the modern `dsmod`/`Set-ADUser` the WinBatch scripts called):

1. `fleet.InventoryFromCommand` — **dynamic inventory**: targets are the stdout lines of any
   command. "Users in an OU" = `ldapsearch … | sed -n 's/^dn: //p'`. Also exposed as
   `--inventory-cmd` on every subcommand (works for cloud APIs, AD groups, anything).
2. `fleet ldapset` — front-end that builds the `ldapsearch` inventory and an `ldapmodify`
   per entry, then runs them through the same engine (pool, dry-run, audit, TUI).

The bind password is resolved (env or `--bind-pw`) and written to a **`0600` temp file**
passed via `-y`, so it never appears on a command line or in the audit log — the rendered
command shows `-y /tmp/…secret`, not the secret.

```
$ fleet ldapset --ldap-url ldap://… --bind-dn cn=admin,dc=lab,dc=local --bind-pw-env LDAP_PW \
      --base ou=people,dc=lab,dc=local --filter "(objectClass=inetOrgPerson)" \
      --attr title --value "Senior Teller" -P 3 --what-if      # dry-run: changes nothing
targets=6  parallel=3  transport=local shell  mode=WHAT-IF (dry run)
total=6  succeeded=6  failed=0  skipped=0
```

Live run, then independent verification with `ldapsearch`:

```
before:  title: pending   (×6)
$ fleet ldapset … --attr title --value "Senior Teller" -P 3
total=6  succeeded=6  failed=0  skipped=0
after:   cn: Ann Teller / title: Senior Teller
         cn: Bob Teller / title: Senior Teller   … all 6 …
```

One command set an attribute on every user in the OU — the exact "set a property on every
user in a given OU" task, proven end-to-end with a dry-run, a bounded pool, and a redacted
audit trail. Swap the filter to `(&(objectCategory=person)(objectClass=user))` and point
`--ldap-url` at a domain controller and it's an AD operation. (Found while building it — a
fourth gap, of sorts: the tool had no dynamic inventory at all; now it does.)
